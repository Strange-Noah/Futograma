# Durable GitHub production reporting

The private data repository branch `production-reports` is report-only. Read `reports/production/latest.json`, `reports/production/runs/<GitHub-run-id>.json` and retained `reports/production/attempts/<run-id>-<attempt>.json` directly through GitHub. It is never an authoritative SQLite location. Keeping reports on a separate branch prevents report commits from invalidating exact database/site commit checks.

The daily production workflow writes reports in an `always()` step, including failed/incomplete operations. A report-upload/readback failure fails the workflow; no report may be assumed to exist from a green ingestion step alone. `workflow_conclusion` is the operation job conclusion before the reporting step; a successful report upload is independently confirmed by byte readback. Check the linked Actions run for infrastructure cancellation or reporting failure after that point. No local process, external monitor, ephemeral artifact, or log is needed for normal receipts. A runner terminated before the final reporting step can leave the previous latest receipt; its run ID/timestamp must never be interpreted as the new run's success.

Counts distinguish new/updated facts and unchanged accepted history. Actually checked club statuses and source results are separate; unchanged history does not prove a source was checked. Missing completion evidence is FAILED_OR_INCOMPLETE, never zero-new-match success. Retained raw evidence and retry queues stay in GitHub snapshots/releases. Reports preserve source failures, quarantine states, versions, retries and publication status. No scheduled report deletion or snapshot pruning is enabled.

Production application/website remain pinned to reviewed `6e3078bb15ca2e83323e80af86f7234e54910fd8`; separately pinned release/reporting tools change only snapshot-publication timing and durable receipts. The first formal collection guard remains `2026-10-31T16:00:00+08:00` in the application. Promotion retains expected source/production heads, exact application code/hash, atomic CAS, upload readback, backup and rollback gates.

An independent `always()` finalizer job writes the actual operation-job conclusion even if that job failed or timed out before its own reporting step. A missing receipt is recorded FAILED_OR_INCOMPLETE with unknown counts, never inferred success. If GitHub cancels the entire workflow or its reporting infrastructure itself is unavailable, compare the durable run ID/timestamp with Actions; no system can guarantee a write when GitHub cannot execute any reporting job.
